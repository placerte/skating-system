# Scope / Problem Framing

## Context
The Skating System application aims to provide a keyboard‑first, inspection‑friendly scoring tool for competitions using the Skating System rules (including recursive tie-breaking rules 5–8).

The primary feature is:
- A scoring matrix (judges × entries)
- A fully transparent, structured explanation trail

Earlier iterations invested heavily in domain scaffolding (Event, Competition, Entry, Participant, persistence). This handoff refocuses the product around a **matrix‑first workflow**, while preserving the domain model in the background.

## Core Product Goals

1. Matrix-first experience (fast, frictionless input)
2. Strict 1‑to‑1 mapping between UI table and computed full table
3. Fully transparent recursive decision transcript
4. Explicit recompute lifecycle (no silent mutations)
5. Minimal domain exposure in v1

## 1. Conceptual Semantics

### S-260210-1.1 Active / Dead Cells
- Active/Dead is a derived, step-local UI concept.
- Not persisted.
- Recomputed on each scoring pass.
- Logs describe contribution but do not store active/dead flags.

### S-260210-1.2 Majority Marker
- `*` indicates factual majority (≥ threshold) at the current step.
- It does NOT indicate decisiveness.
- Majority markers may appear in dead cells.
- Relevance is conveyed by active/dead styling and transcript.

### S-260210-1.3 Full Table vs UI Table
- UI table is a strict projection of the full computed table.
- 1-to-1 mapping between UI cells and full-table cells.
- UI may hide, dim, reorder — never merge or aggregate.

---

## 2. Algorithm Boundaries

### S-260210-1.4 Recursive Transparency
- Solver emits full recursive decision trail.
- Trail is a structured tree.
- Each node contains rule applied and subset of entries.
- Tie-break branches explicitly visible.

### S-260210-1.5 Cutoff Definition
- Cutoff is row-local and step-local.
- Cutoff = last rank column that participates in determining that row’s outcome at that step.
- Formally, for entry E at a given decision node, k_E is the maximum rank index that the solver had to inspect/compare in order to determine E’s relative standing within that node’s subset.
- Contributing region is always contiguous prefix {1..k_E}.
- Columns > k_E are dead (styling only).
- k_E is derived directly from the solver’s comparison depth for entry E at that node (not from UI state).

### S-260210-1.6 Cell Semantics
- Prefix columns (1..i) contain `X (Y)`:
  - X = cumulative count of ranks ≤ i
  - Y = cumulative sum of those ranks
- `0 (0)` is a valid computed state.
- `0 (0)` is always styled as dead.

### S-260210-1.7 Missing Ranks
- Solver refuses to compute if any judge rank is missing or invalid.
- "Missing" includes blank cells or structurally invalid judge input (e.g., duplicate ranks within a judge, out-of-range values).
- Missing ranks are not auto-resolved.

---

## 3. Matrix-First UX Contract

### S-260210-1.8 Inline Creation
- Matrix can implicitly create Entries and Judges.
- Free-string workflow.
- Domain heaviness hidden.

### S-260210-1.9 Exact String Reuse
- Exact string match reuses existing Entry.
- No normalization/fuzzy matching in v1.

### S-260210-1.10 Judge Lettering
- Letters are column indicators.
- Letters are recomputed from current column order on every render (1st = A, 2nd = B, etc.).
- Re-packed after reorder or deletion.
- Not stable identifiers and never persisted as identity.

### S-260210-1.11 Focus Rules
- Default focus: top-left editable cell.
- Adding row/column does not move focus.
- Display toggles preserve semantic focus.

### S-260210-1.12 Navigation Structure
- Event screen lists competitions.
- Entering competition opens Matrix screen.
- No required domain management screens in v1.

---

## 4. Styling & Symbol Rules

### S-260210-1.13 Symbol Precedence
- No special symbol for decisive majority.
- Transcript explains decisiveness.

### S-260210-1.14 Placement Column
- Final placements displayed in dedicated rightmost column.
- No full-row emphasis required.

### S-260210-1.15 Dead Styling
- Dead cells use contrast/dimming only.
- No additional glyphs.

### S-260210-1.16 Majority Scope
- `*` only appears in prefix aggregate columns.
- Never in judge input columns.

---

## 5. Explanation / Transcript Model

### S-260210-1.17 Transcript Structure
- Solver generates structured tree of text nodes.
- Each node contains:
  - narrative text
  - rule identifier (e.g., Rule 5 / 6 / 7 / 8)
  - subset of entries considered at that node
  - children (tie-break branches)
- Generated incrementally during solving.
- Transcript structure must be deterministic for identical input matrices.

### S-260210-1.18 UI Behavior
- UI renders transcript only.
- No interactive cell→node mapping required.

### S-260210-1.19 Edit Lifecycle
- After rank edit: mark results as STALE.
- Explicit recompute required.

---

## 6. Persistence Lifecycle

### S-260210-1.20 Persistence Scope
- Persist inputs only (metadata + rank matrix).
- Do not persist derived results or transcript.

### S-260210-1.21 Load Behavior
- Auto-recompute on load (configurable, default ON).
- If auto-recompute is OFF, application loads in STALE state until manual recompute.
- Do not compute if ranks incomplete.

### S-260210-1.22 Schema Versioning
- Persisted files include schema_version.
- Optional app_version field.

# Implementation (Suggestions Based on Current Codebase)

## Architecture
- Keep domain models (Event, Competition, Entry, Judge).
- Add Solver service responsible for:
  - Computing placements
  - Producing transcript tree
  - Producing full-table derived state

## Data Structures
- `DecisionNode { text: str, rule_applied: str, subset_entries: list[str], children: list[DecisionNode] }`
- `SolveResult { placements, derived_table, transcript_root }`

## Matrix Screen
- Operates directly on Competition.
- Inline create methods for Entry/Judge.
- Strict projection of derived table.

## Recompute Flow
- Maintain `is_stale` flag.
- Recompute clears stale and regenerates transcript.

- No advanced judge weighting.
- No domain normalization workflows.
